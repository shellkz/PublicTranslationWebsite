# 架構規格

本文件是「資料結構」與「Build 輸出結構」的技術規格,取代 [專案規劃.md](./專案規劃.md) 中對應章節的草稿版本。翻譯者實際參與流程與操作步驟,見 [翻譯者指南.md](./翻譯者指南.md)。

---

## 1. 核心設計原則

貫穿本文件所有結構的兩條原則:

1. **識別碼優先順序:外部權威 ID > 來源站自身編號 > 自訂 slug**
   任何「人」或「作品」實體的識別碼,優先採用可供多人獨立查詢、能自然收斂到同一結果的外部 ID(Wikidata QID),其次是來源站(青空文庫/古騰堡)自身的編號,自訂 slug 是最後手段。理由:識別碼若靠每個貢獻者自己發明命名,不同人各自造出不同名稱,同一實體會分裂成多筆——外部 ID 是一個大家都能查到同一答案的公共參照點。

2. **身分只存一份,不在多處重複填寫**
   一個實體的識別碼一律由「路徑/資料夾名稱」表達。凡是已經能從路徑推得的資訊(檔名即 UUID、資料夾名即譯者 ID),不再要求於檔案內容中重複填寫——避免路徑與內容各自更動後彼此不同步的風險。這條原則不只適用於識別碼本身,也適用於「屬於作品的事實」:作者、原文語言、tags、category 這些不會因為譯者不同而不同的事實,一律只存在 `/content/works/{work-id}/` 一份,`{uuid}.md` 透過 `work_id` 反查取得,不重複填寫。實體之間用「引用」欄位(`work_id`、`author_id`)串接,不用巢狀存放。

- **文章 ID 用 UUID,不用流水號**:多人分散式 PR 提交,流水號需要中心化協調(撞號風險、merge 時要重新計算),UUID 完全繞開這個問題,天生適合無中心化協作。實際檔名格式後來演變成「可讀前綴 + UUID」,但輸出網址仍只採用 UUID 那段,理由與細節見架構規格.md 4.1。
- **URL 設計原則**:只做 build 時就窮舉產生的靜態單一資源 URL(如 `/translations/{uuid}/`、`/works/{id}/`),不做動態多條件查詢組合(`?tag=X&sort=Y` 這類改用前端 JS 記憶體 filter,不對應獨立網址),不做 HTTP 寫入動詞——寫入操作一律走 GitHub PR 流程。

## 2. Repo 原始碼結構

Repo 根目錄分四塊,依「誰會去動它」分開,彼此不混:

```
/docs/                                    ← 規格與指南文件(本文件所在處)

/content/                                 ← 譯者實際會碰的地方,詳見下方
    /translators/{譯者id}/                  本站譯者(ID = 資料夾名稱,建議採 GitHub 帳號)
        description.md                       譯者 profile(選填,詳見 3.1)
        {標題slug}_{uuid}.md                 譯文,frontmatter + 正文(詳見 4),例:hashire-merosu_a1b2c3d4-e5f6-4a1b-9c2d-1234567890ab.md

    /works/{slug}_{外部id}/                  原作品(抽象層,與翻譯版本無關),例:ningenshikaku_Q212321/
        description.md                       詳見 3.2

    /source-authors/{slug}_{外部id}/         原作者(第三方,非本站帳號)
        description.md                       詳見 3.3

    /source-translators/{slug}_{外部id}/     中間語言譯者(多層翻譯鏈才需要,如法文原作經英譯再中譯)
        description.md                       詳見 3.4

/scripts/                                 ← Node.js build script 本體(讀 content/,產生靜態頁面),跑在 Node,不出現在瀏覽器裡

/assets/                                  ← 依附在輸出 html 上、跑在瀏覽器端的 JS/CSS(hover 顯示註解、filter 搜尋等)
    js/
    css/

/CONTRIBUTING.md
/LICENSE
```

`content/`、`scripts/`、`assets/` 三者職責不重疊:`content/` 是純資料(給 build script 讀),`scripts/` 是產生網站的邏輯(build 時跑一次,不出現在最終網頁裡),`assets/` 是網站本身的前端資源(不參與 build 邏輯,只是被複製/打包進輸出)。三者是平行關係,不互相巢狀。

**新增時機**:`content/works/`、`content/source-authors/`、`content/source-translators/` 底下的資料夾,由第一個需要引用該實體、卻在既有清單中找不到對應項目的譯者,在同一個 PR 中一併新增(見翻譯者指南)。沒有「事先建好資料庫」這回事——這個架構沒有後端,PR 是唯一的寫入機制。

## 3. description.md 規格

一共四種身分,各自一份 `description.md`,不共用同一份規格:

| 身分 | 路徑 | 用途 |
|---|---|---|
| 本站譯者 | `/content/translators/{id}/description.md` | 個人 profile,選填 |
| 原作品 | `/content/works/{id}/description.md` | 抽象作品層,連結原作者、列出已知來源版本 |
| 原作者 | `/content/source-authors/{id}/description.md` | 第三方,非本站帳號 |
| 中間語言譯者 | `/content/source-translators/{id}/description.md` | 多層翻譯鏈才需要 |

### 3.1 `/content/translators/{譯者id}/description.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `display_name` | 選填 | 顯示名稱,不填則顯示資料夾名稱 |
| `bio` | 選填 | 自我介紹 |
| `links` | 選填 | 外部連結陣列(個人網站、其他社群帳號等) |

整份檔案可以不存在——沒有 description.md 時,譯者頁只顯示資料夾名稱與作品列表,不擋 build。

### 3.2 `/content/works/{work-id}/description.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `wikidata_id` | 選填(建議) | 作品的 Wikidata QID,若存在則 build 時自動抓取多語言標題等資料 |
| `title` | 有 wikidata_id 則選填,否則必填 | 標題(至少一種語言),做為 Wikidata 抓取失敗時的 fallback |
| `author_id` | 必填 | 指向 `/content/source-authors/{id}/` |
| `original_language` | 必填 | 原作最初寫成的語言 |
| `tags` | 選填 | 主題標籤,屬於作品本身,不因譯者不同而不同 |
| `category` | 選填 | 分類,屬於作品本身 |
| `excerpt` | 選填 | 作品本身的摘要,一部作品一份,跟每篇譯文自己的 `excerpt`(見 4.2)是不同層級的東西,不衝突同名。目前站上尚未有內容,欄位先開著 |
| `original_publication_date` | 選填 | 原作寫成/首次發表的時間,**不是** `editions[].date`(那是某個特定印刷版本的出版年份,常常是後來的重印,不等於原作寫成時間)。目前站上尚未有內容,欄位先開著;之後若拿來做篩選/排序,空值一律視為「通過」,不因為沒填就被篩掉或當成最小值處理 |
| `editions` | 選填 | 已知來源版本列表,陣列。同一部作品可能同時存在多種語言的來源文本(如日文原文在青空文庫、英譯本在古騰堡),每項各自記錄一份來源,欄位見下 |

`editions` 每一項的欄位:

| 欄位 | 必填 | 說明 |
|---|---|---|
| `url` | 必填 | 該版本的來源連結 |
| `language` | 必填 | 該版本文本的語言 |
| `publisher` | 選填 | 出版社/底本 |
| `date` | 選填 | 出版日期 |
| `copyright_status` | 必填 | 該版本文本實際的公版/著作權狀態,自由文字,照實際情況填寫(如「日本公版」「1929年前出版,美國公版」),不是從固定列舉值挑選——按原文實情記錄,不強制對應到預先定義的分類。與譯文自身授權(全站固定 CC BY-SA 4.0,見 [/LICENSE](../LICENSE))是兩件事 |
| `translator_id` | 選填 | 若該版本本身就是翻譯(如古騰堡的英譯本),指向 `/content/source-translators/{id}/` |

**不存放**:任何特定中譯所用的細節(那屬於個別 `{uuid}.md` 的 `edition_url`,指向 `editions` 裡的某一項)。

**`work-id`(資料夾名)與 `wikidata_id`(欄位)的關係**:資料夾名建議嵌入外部 ID(如 `ningenshikaku_Q212321`),但那只是幫助不同貢獻者各自查找時容易收斂到同一個資料夾名的**命名慣例**,不是 build 時實際依賴的資料來源——`work_id` 本身是一個不透明的參照鍵,一旦被 `{uuid}.md` 引用就不該再改。真正給 build script 打 API 用的,是 description.md 內的 `wikidata_id` 欄位;這個欄位可以獨立修正(比對錯條目、需要合併重複項目等情況),只改這一個檔案,不牽動任何引用這個 `work_id` 的翻譯檔案。

**給讀者看的作品標題,一律用 `title.zh`,不做語言 fallback**:凡是「這部作品叫什麼」這種給一般讀者辨識用的標題顯示(如全作品列表頁的封面、麵包屑),直接取 `title.zh`,不會因為沒填就退回顯示日文/英文等原文——顯示讀者看不懂的原文對他們沒有意義,尤其是放大呈現的情況。原文標題只在明確標示「這是原文」的小字場合使用(如 `/works/{id}/` 頁面 H1 上方的小字、`/translations/{uuid}/` 頁面標題上方的小字),用來源優先序 `ja → en → romaji → zh` 挑選,兩種用途不要混用同一個值。

### 3.3 `/content/source-authors/{author-id}/description.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `wikidata_id` | 選填(建議) | 作者的 Wikidata QID,若存在則 build 時自動抓取姓名(多語言)、生卒年、簡介 |
| `names` | 有 wikidata_id 則選填,否則必填 | 姓名物件,依語言分 key,例:`{ja: "太宰治", romaji: "Dazai Osamu"}` |
| `aliases` | 選填 | 其他曾用名/譯名,輔助日後查重比對 |
| `source_url` | 選填 | 來源站(青空文庫/古騰堡)作者頁連結 |

無 Wikidata 條目時,`names`/生卒年/簡介需手動填寫,屬於較少數情況。

### 3.4 `/content/source-translators/{translator-id}/description.md`

| 欄位 | 必填 | 說明 |
|---|---|---|
| `names` | 必填 | 姓名 |
| `language` | 必填 | 該譯者的譯入語言(即本站譯文的「來源語言」) |
| `wikidata_id` | 選填 | 若有 |
| `source_url` | 選填 | 來源站作者/譯者頁連結 |

## 4. 譯文檔案 `{uuid}.md` 規格

### 4.1 路徑與檔名

`/content/translators/{譯者id}/{標題slug}_{uuid}.md`

- 檔名格式是「可讀前綴 + UUID」,例:`hashire-merosu_a1b2c3d4-e5f6-4a1b-9c2d-1234567890ab.md`
- `{uuid}` 由 `/tools/new-translation/` 工具或 scaffold 腳本以 `crypto.randomUUID()` 產生,**不需要、也不應該由譯者手動輸入**
- 可讀前綴由工具**自動從譯者已經填寫的 `title` 欄位 slugify 產生**,不需要譯者額外輸入。前綴用譯者自己語言書寫也完全可以(例如中文譯者會產生 `奔跑吧梅洛斯_{uuid}.md`),純粹是給人瀏覽自己資料夾時辨識用,不影響任何機制
- 前綴是**非權威、不被解析的裝飾性資訊**:真正的身分識別碼是檔名中符合標準 UUID 格式的那一段,build script 用固定格式比對規則(而非依位置切割字串)擷取這段當作 canonical id;`/translations/{uuid}/` 的輸出網址也只採用這段 UUID,不包含可讀前綴,以確保網址不會因為譯者事後修改 `title` 而跟著改變
- frontmatter 內不重複填寫 `id` 欄位
- 工具自動產生檔名時,建議統一正規化為 Unicode NFC 形式,避免 macOS 與其他系統之間因檔名正規化方式不同(NFD vs NFC)造成 git 誤判檔案異動

### 4.2 Frontmatter 欄位

| 欄位 | 必填 | 型別 | 說明 |
|---|---|---|---|
| `work_id` | **必填** | string | 指向 `/content/works/{id}/`,build 時驗證存在。作者、原文語言、tags、category 都透過這個反查,不在此重填 |
| `edition_url` | **必填** | string | 這次翻譯實際依據的來源連結。build 時比對 `work.editions[].url`;若沒有對應項目,PR 需一併在該作品的 `editions` 補上這筆來源 |
| `title` | 必填 | string | 這篇譯文自己的標題(可與原作標題不同,是譯者的用詞選擇);同時也是檔名可讀前綴的生成來源 |
| `language` | 選填 | string | 這篇譯文本身寫成的語言。目前站上固定只收中文譯本,實務上用不到,先保留欄位供未來若支援多目標語言時使用 |
| `date` | 必填 | string | 提交日期 |
| `excerpt` | 選填 | string | 手動填寫,索引頁摘要用,不做自動截取 |

`translator` 不列為欄位——由路徑 `/content/translators/{譯者id}/` 推導。`id` 不列為欄位——由檔名中的 UUID 段推導。`author_id`/`source_translator_id`/`source_language`/`original_language`/`source_publisher`/`source_date`/`source_copyright_status`/`tags`/`category` 都不列為欄位——全部是 `work`(或 `work.editions`)的事實,透過 `work_id` + `edition_url` 反查取得。

`license` **也不列為欄位**:全站譯文授權固定是 CC BY-SA 4.0(見 [/LICENSE](../LICENSE)、[/CONTRIBUTING.md](../CONTRIBUTING.md)),這是專案層級的固定政策,不是逐篇填寫、也不是逐作品查詢的事實。build 產生每篇譯文頁面時直接套用這個固定值,不需要、也不該讓譯者在自己的檔案裡重複打一次同樣的字。

## 5. Build 輸出結構

以下路徑是 build 之後**部署到網站上的公開網址**,跟第 2 節的 repo 原始碼路徑是兩棵獨立的樹——公開網址不帶 `/content/` 前綴(讀者看到的是 `/works/{id}/`,不是 `/content/works/{id}/`),避免把內部檔案結構外露成公開 URL 的一部分。

```
/translations/{uuid}/index.html                   ← 單篇譯文全文,純靜態,含 canonical,不依賴 JS
/translations.json                                ← 全站譯文 metadata(不含全文),前端搜尋/篩選用
/works/index.html                                 ← 全作品列表頁(work-level,一部作品一張卡),見 5.1
/works/{work-id}/index.html                       ← 作品資訊頁:列出此作品在站內的所有譯本(標題摘要+連結)
/tags/{tag}/index.html                            ← 標籤索引頁,摘要+連結
/translators/{譯者id}/index.html                  ← 譯者 profile + 作品列表
/source-authors/{author-id}/index.html            ← 原作者 profile + 站內譯本列表
/source-translators/{translator-id}/index.html    ← 中間譯者 profile + 相關作品列表
```

**關鍵原則沿用專案規劃.md**:每篇譯文只有一份實體內容(`/translations/{uuid}/`),其餘所有索引頁(`/works/`、`/tags/`、`/translators/`、`/source-authors/`、`/source-translators/`)都只是「摘要 + 連結列表」,不重複存全文。

### 5.1 `/works/` — 全作品列表頁(work-level)

一部作品一張卡,**不分譯本**——理由:讀者的搜尋意圖是「找一個故事來看」,不是「找某一篇譯文」,同一部作品有好幾個譯本時,列成好幾張長得很像的卡片反而混淆,而且會跟 `/works/{work-id}/`(見 5.2)的功能重疊。這頁只負責「這裡有哪些作品」,選定作品之後要看哪個譯本,交給 5.2 那頁處理。

- 卡片顯示:`title.zh`(封面 + 卡片標題,見 3.2 的顯示標題慣例)、原作者、站內譯本數量(封面右下角小標籤「N 個譯本」,**0 個特別標紅**,方便譯者掃到可認領的作品)
- **尚無譯本的作品也會列出來**,不是只列有翻譯的——這頁同時是「作品目錄」跟「翻譯者尋找認領目標」的入口
- 可篩選欄位:作品標題(文字,partial match)、原作者(文字,partial match)、譯者(文字,partial match;一部作品可能有多位譯者,任一位符合就算)、分類(下拉)、原文語言(下拉)、標籤(checkbox 多選,可複選)
- 篩選邏輯**完全在瀏覽器端跑**:build 時所有卡片已經連同 `data-*` 屬性完整輸出到 HTML 裡,`assets/js/works-filter.js` 只是讀這些屬性做比對、切換顯示/隱藏,沒有 JS 一樣能看到完整未篩選清單
- 首頁的搜尋框(純文字,見 homepage.js)導向 `/works/?q=...`,這頁的 JS 讀網址參數自動預填並套用

### 5.2 `/works/{work-id}/` — 資訊卡頁(對應青空「card」頁 / 古騰堡「ebooks」頁)

顯示「這部原作」本身的資訊,不含任何譯文全文:

- 作品標題(原文標題 + 站內各譯本各自取的標題)
- 原作者:連結 `/source-authors/{author-id}/`,帶顯示姓名/生卒年摘要
- 原文語言(`original_language`)、tags、category
- 已知來源版本(`editions`):每項顯示語言、出版資訊、版權狀態——同一部作品可能同時有多種語言的來源(如日文原文 + 英譯本),各版本狀態可能不同,並列顯示,不取單一值蓋過去
- **站內所有譯本列表**:每個譯本一行,顯示譯者(連結 `/translators/`)、依 `edition_url` 對應到的 `editions` 項目取得語言(若該項目有 `translator_id` 則一併連結中間譯者)、`excerpt`、連結到對應的 `/translations/{uuid}/`

這一頁存在的理由,就是讓「同一部作品的多個譯本」有地方被同時看見、互相比較——這是本站跟青空/古騰堡最大的結構差異(它們不會同時收多個競爭譯本)。

### 5.3 `/translations/{uuid}/` — 內容頁

進入即直接是這篇譯文的正文,不重複作品頁上的完整 metadata。仍保留最小必要的頭尾資訊,呼應青空/古騰堡內容頁「底部放底本資訊區塊」的慣例:

- 頁首:標題、譯者連結、回作品頁連結
- 正文:全文
- 頁尾(精簡版引用區塊,非完整 metadata):`edition_url`、`license`、原作者連結、canonical link

頁尾這幾項是「引用」不是「資料重複」——完整的作品層資訊只存在 `/works/{work-id}/`,這裡只放讀者當下讀這篇譯文就需要知道的最小引用資訊。

## 6. 驗證規則(build-time / CI)

**目前的執行時機**:以下檢查目前是 `build.js` 的一部分,實際只在 Cloudflare 部署時(即 merge 進 `main` 之後)執行,PR 階段還沒有另外接一支會在 merge 前擋錯誤的 GitHub Actions——也就是說,PR 通過與否目前純粹取決於是否有人去看,不是自動化把關。要讓「自動檢查通過即可合併」這個政策(見[專案規劃.md](./專案規劃.md)、[翻譯者指南.md](./翻譯者指南.md#8-自動檢查))名副其實,需要另外設一支在 `pull_request` 事件上執行 `node build.js`(或抽出其中驗證邏輯)的 workflow,並設成必要的 status check——這件事尚未做,列在第 7 節開放項目。

- **參照完整性檢查**:`{uuid}.md` 的 `work_id` 若指向不存在的資料夾,build 直接失敗;`work.author_id` 若指向不存在的資料夾,同樣失敗;`editions[].translator_id`(若有填)指向不存在的資料夾也失敗。等同於用 build script 充當資料庫外鍵約束。
- **來源比對檢查**:`{uuid}.md` 的 `edition_url` 應能在對應 `work.editions[].url` 中找到相符項目;找不到時 build 失敗,提示需在該作品的 `editions` 補上這筆來源,而不是放任一筆孤立、未登記的來源存在。
- **Wikidata 抓取**:build 時依 `wikidata_id` 呼叫 API 抓取姓名/生卒年/簡介等內容並快取進輸出頁面;抓取失敗時 fallback 到 description.md 中手動填寫的欄位(若無則顯示 ID 本身,不擋 build)。
- **新增條目相似度檢查(lint,非阻擋性)**:PR 中新增 `/content/works/`、`/content/source-authors/`、`/content/source-translators/` 資料夾時,比對既有資料夾的 `wikidata_id`/`names`/`aliases`,發現高相似度就在 PR 上留警告,交給 reviewer 判斷是否為重複。**目前先不做**——這屬於自動化輔助,重複偵測初期先完全依賴 reviewer 人工比對,值得做但不是必要條件,先記錄在此,等實際發生重複問題再評估。

## 8. 部署

**上線網址**:https://publictranslationwebsite.shell-prisoner.workers.dev/

**託管方式**:Cloudflare 現行的專案建立流程走的是 **Workers(靜態資源)**,不是舊版 classic Pages 的「git 整合 + build command + output directory」三欄位介面,而是 **Build command + Deploy command** 兩欄位,輸出目錄改在 `wrangler.toml` 裡設定。實際效果跟 `專案規劃.md` 原本規劃的「push 即自動觸發 build + 部署,不需要另外寫 GitHub Actions」一致,只是 Cloudflare 這邊的產品/介面名稱從「Pages」變成「Workers 靜態資源」——純粹是 Cloudflare 自己的產品演進,build 出來的仍然是純靜態檔案,沒有用到 Workers 的動態執行邏輯或 KV,不違反「避免用到 Cloudflare Workers/KV」的原則。

**設定內容**(Cloudflare Dashboard → 該 Workers 專案 → Build configuration,這些是**只存在 Dashboard 裡、沒有進版控**的設定,重新建立專案時要照這裡手動填回去):

- Root directory:`/`
- Build command:`npm install && cd scripts && npm install && node build.js`
- Deploy command:`npx wrangler deploy`
- Version command:`npx wrangler versions upload`
- Branch control:Production branch 設為 `main`;「Builds for non-production branches」有勾選,代表 push 到任何分支都會觸發一次 build(非 `main` 分支會是 preview 部署,不影響正式網址)
- Build watch paths:
  - Include:`content/**`、`scripts/**`、`assets/**`、`wrangler.toml`、`package.json`、`package-lock.json`
  - Exclude:`node_modules/**`、`.git/`
  - 意味著**只改 `docs/`、`CONTRIBUTING.md`、`LICENSE` 這類不影響 build 輸出的檔案不會觸發重新部署**(本來就不需要,因為這些檔案不參與 `dist/` 的產生)

**相關檔案**(這些有進版控,重建專案時不用重填,repo 裡就有):
- `/wrangler.toml`——宣告 `[assets] directory = "dist"`
- `/package.json`——根目錄的 devDependency,釘住 `wrangler` 版本(避免每次 deploy 都重新解析版本、行為漂移)
- `/scripts/package.json`——build script 自己的依賴(gray-matter、markdown-it)

**目前狀態**:2026-08-14 起先移除 Cloudflare 上的 Worker 專案,暫時不公開上線(原因見翻譯者指南/CI 尚未補齊,不想讓未完成流程被外部看到)。之後要重新上線時,回 Cloudflare 建一個新 Workers 專案,照上面「設定內容」原樣填一次即可,不需要改動 repo 裡任何檔案。

**GitHub Pages 備援**:尚未設定,見第 7 節開放項目。
